# Host-ladder change with an unchanged GPU table kernel

This is a distinct public table-construction experiment. It does **not** combine the host candidate with the earlier GPU inversion-batching kernel. Both arms call one byte-identical frozen `kernel_build_gtable` definition through the same launch site. The only selected behavior is original `gt_build_ladders` versus the already isolated `batch_ladders`. The manifest pins the source tree, math header, checked OpenSSL wrappers, host candidate and exact original kernel extraction.

No solver, search, recovery, transaction parsing, wallet input, or production integration is generated. The same experiment-only deprecated OpenSSL API limitation described in README.md applies. The build extracts only geometry, the table kernel, affine export, ladders and the independent OpenSSL table spot checker. The checked-in GPU inversion-batching candidate is never read by this preparation script.

Before retaining timing samples, the fixed public scalars 1, 17 and the prior dense 248-bit test integer each pass:

- All 19,200 original/batched ladder slots compared, with all 7,198 padding slots independently checked zero.
- Entire 1,048,576-record GPU tables compared byte-for-byte, using distinct initial output bytes to expose unwritten slots.
- 252 direct OpenSSL scalar-multiplication table checks on **each arm** (60 chunk corners and 192 deterministic sampled positions).

Seven alternating baseline/candidate pairs then use public scalar 1. Each construction includes host ladder allocation/generation, device allocation/upload/initialization, the identical original kernel, download, the same 252 OpenSSL checks and all per-construction cleanup. Host ladder vector destruction belongs to cleanup. The reported wall stages partition the total interval. CUDA-event kernel time is nested within kernel wall time and must not be added to those stages. Preallocated caller output buffers and post-pair full comparisons/hashing/reporting are outside the interval equally for both arms. Context initialization is also excluded. These are instrumented public table construction timings, **not solver throughput**; no speedup can be inferred from source preparation, local compilation or code generation.

`--correctness-only` runs all three fixed scalar checks without retained timing samples for sanitizer runs. This experiment does not inject exceptional GPU-kernel inputs and makes no new exceptional-kernel coverage claim. Earlier kernel evidence concerns the previously tested kernel and does not replace the new host-data correctness gate. CPU zero/order rejection evidence is a separate prerequisite. All normal/sanitizer output, binary hashes, runtime identities and caller exit statuses must be collected and independently validated before any performance conclusion.

Build from repository root with Dockerfile.gpu; `/results` contains `table-gate`, generated source, manifest, exact original kernel snippet, GPL license, compiler/build logs, disassembly, binary hash and dependency listing. Preparation rejects stale source/candidate hashes before creating outputs and never overwrites an existing directory. The binary accepts a fresh output JSON path plus the optional fixed correctness-only flag. It accepts no arbitrary scalar input. A caller must impose an outer timeout and ensure failed/truncated reports are never treated as passing evidence. Cloud execution/staging/receipt validation belongs to the separately reviewed controller; no cloud operation is performed here.

The timing is a **warm, instrumented construction** measurement, not the exact production timer: host output-vector allocation and context warmup are excluded, while GPU output allocation, sentinel initialization, events and cleanup are included. Only scalar 1 is timed; scalar 17 and dense248 are correctness fixtures. Since GPU kernel bytes and launch geometry are unchanged, any kernel-event timing differences are diagnostic variation and are not evidence of a kernel optimization.

`stage_gpu.py` retains the bounded HTTPS/ZIP transport from the earlier isolated table experiment, but binds `experiments/host-ladder-batch/host-gpu.sh` and the committed `ops/aws-gpu-execution/ready.sh` explicitly. The remote basename remains `host.sh` solely for transport compatibility. Each script is retrieved by a full committed SHA and its bytes are checked against local committed source hashes; a validated root `table-gate` binary is the only archive member extracted. The staging renderer cannot establish that its supplied artifact identity has valid build provenance: the operator must independently verify the CI run, source manifest, binary and kernel identities before rendering/launching.
